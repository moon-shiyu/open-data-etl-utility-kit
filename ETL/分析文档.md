# 标准 ETL 启动链路分析文档

## 1. 文件概览

| 文件 | 角色 | 说明 |
|---|---|---|
| `ETL/ETL_Setup.sh` | 环境初始化脚本 | 设置时间戳 `NOW`、追加 JDK 到 `PATH`、定义 `ETL_ROOT_DIR` 三个基础环境变量 |
| `ETL/Setup-Script.sh` | 具体 ETL 任务的入口脚本（模板） | source 环境初始化脚本 `ETL_Setup.sh`，定义三个业务参数（`ETL_NAME`/`ETL_DIR_RELATIVE`/`DATA_SYNC_ETL`），然后 source 标准启动脚本 |
| `ETL/Standard_ETL.sh` | 标准启动器 | 接收三个位置参数，调用 Kettle `kitchen.sh` 执行 `Standard_ETL.kjb`，并将 stdout 重定向至日志文件 |
| `ETL/Standard_ETL.kjb` | Kettle Job（XML） | 编排实际 ETL 流程：设置变量 → 查询邮件地址 → 运行 KTR → 根据成功/失败发送通知邮件 |

> **注意：** 文件名容易混淆。`ETL_Setup.sh` 是底层**环境初始化**脚本（设置 NOW/PATH/ETL_ROOT_DIR）；`Setup-Script.sh` 是面向每个 ETL 任务的**入口模板**（每新建一个 ETL 任务复制此文件）。命名上 "ETL_Setup" 偏向基础设施，"Setup-Script" 偏向具体任务配置。

## 2. 完整执行链路

### 2.1 调用关系图

```
用户 / cron 执行
    |
    v
Setup-Script.sh                        <-- 入口脚本（每个 ETL 任务一份副本）
    |
    |  第 1 行: source (.) /path/to/.../ETL/ETL_Setup.sh
    |           (占位路径，部署时替换为 ETL_Setup.sh 的真实路径)
    |      => NOW=<YYYYMMDD_HHMMSS>    时间戳
    |      => PATH 追加 JDK bin        确保 java 可用
    |      => ETL_ROOT_DIR=<绝对路径>   ETL 根目录
    |
    |  第 3-5 行: 设置三个业务参数
    |      ETL_NAME=<KTR 文件名，不含 .ktr>
    |      ETL_DIR_RELATIVE=<KTR 所在子目录，以 / 结尾>
    |      DATA_SYNC_ETL=<Y|N>
    |
    |  第 7 行: echo 启动日志（使用 $NOW 和 $ETL_NAME）
    |
    |  第 9 行: source (.) $ETL_ROOT_DIR/Standard_ETL.sh $ETL_NAME $ETL_DIR_RELATIVE $DATA_SYNC_ETL
    v
Standard_ETL.sh                        <-- 标准启动器
    |
    |  接收位置参数:
    |      $1 => ETL_NAME
    |      $2 => ETL_DIR_RELATIVE
    |      $3 => DATA_SYNC_ETL
    |
    |  调用:
    |    ../data-integration/kitchen.sh \
    |        -file="$ETL_ROOT_DIR/Standard_ETL.kjb" \
    |        -param:P_ETL_Transformation_Directory=$ETL_DIR_RELATIVE \
    |        -param:P_ETL_Transformation_Name=$ETL_NAME \
    |        -param:P_Data_Sync_ETL=$DATA_SYNC_ETL \
    |        -level=Detailed \
    |        > "../Log/${ETL_NAME}_${NOW}.txt"
    v
Standard_ETL.kjb                       <-- Kettle Job 引擎执行
    |
    |  参数接收（在 <parameters> 节点中声明）:
    |      P_ETL_Transformation_Name      (KTR 文件名，默认值: 空)
    |      P_ETL_Transformation_Directory (KTR 相对目录，默认值: 空)
    |      P_Data_Sync_ETL               (是否 DataSync，默认值: N)
    |
    |  执行流程 (5 条 hop):
    |      START
    |        --> Set variables
    |              (设置 Data_Sync_ETL, ETL_Transformation_Name, ETL_Specific_To_Addresses)
    |            --> ETL_Specific_To_Addresses.ktr
    |                  (查询该 ETL 对应的通知邮件地址)
    |                --> Run KTR
    |                      (执行 ${ETL_DIRECTORY}${P_ETL_Transformation_Directory}
    |                             ${P_ETL_Transformation_Name}.ktr)
    |                      |--[成功/evaluation=Y]--> ETL_Completion_E-Mail - TRUE
    |                      |--[失败/evaluation=N]--> ETL_Completion_E-Mail - FALSE
    v
日志输出: ../Log/${ETL_NAME}_${NOW}.txt
```

### 2.2 环境变量传递详解

**第一层 -- `ETL_Setup.sh`（环境初始化）**

```bash
NOW=$(date +"%Y%m%d_%H%M%S")                                            # 第 1 行：时间戳
PATH=$PATH:/path/to/jdk/bin                                              # 第 2 行：追加 JDK 路径
ETL_ROOT_DIR=/path/to/directory/open-data-etl-utility-kit/ETL            # 第 3 行：ETL 根目录
```

- 该脚本通过 `source`（`.`）被 `Setup-Script.sh` 加载，因此三个变量直接注入到调用者的 shell 环境中。
- `/path/to/` 是占位符，实际部署时需替换为真实路径。
- `NOW` 在 source 时即被求值，整个 ETL 运行期间保持同一时间戳。

**第二层 -- `Setup-Script.sh`（业务参数定义 + 调度）**

```bash
. /path/to/directory/open-data-etl-utility-kit/ETL/ETL_Setup.sh   # 第 1 行：加载环境初始化脚本

ETL_NAME=Name_of_KTR_file_no_extension     # 第 3 行：KTR 文件名（不含 .ktr）
ETL_DIR_RELATIVE=Directory_containing_KTR_file/  # 第 4 行：相对目录，以 / 结尾
DATA_SYNC_ETL=Y                             # 第 5 行：是否为 DataSync 类型 ETL

echo "ETL $ETL_NAME has started at $NOW."   # 第 7 行：打印启动信息

. $ETL_ROOT_DIR/Standard_ETL.sh $ETL_NAME $ETL_DIR_RELATIVE $DATA_SYNC_ETL  # 第 9 行：调用标准启动器
```

- 这三个变量值是模板占位值，每新建一个 ETL 任务时复制此脚本并填入实际值。
- 第 1 行的 source 路径指向 `ETL_Setup.sh`（环境初始化脚本），部署时需确保路径正确。
- 第 7 行使用 `$NOW`（由 `ETL_Setup.sh` 设置），验证了 source 的执行顺序。
- 第 9 行通过 `$ETL_ROOT_DIR`（同样来自 `ETL_Setup.sh`）拼接出 `Standard_ETL.sh` 的绝对路径。

**第三层 -- `Standard_ETL.sh`（参数映射与 Kettle 调用）**

```bash
ETL_NAME=$1           # 位置参数 1 <-- Setup-Script.sh 传入
ETL_DIR_RELATIVE=$2   # 位置参数 2
DATA_SYNC_ETL=$3      # 位置参数 3
```

Shell 变量通过 `kitchen.sh` 的 `-param:` 语法映射为 Kettle Job 参数：

| Shell 变量 | `-param:` 参数名 | Kettle Job 参数名 | Job 内用途 |
|---|---|---|---|
| `ETL_DIR_RELATIVE` | `P_ETL_Transformation_Directory` | 同名 | 拼接 KTR 文件的相对路径 |
| `ETL_NAME` | `P_ETL_Transformation_Name` | 同名 | KTR 文件名（不含 .ktr） |
| `DATA_SYNC_ETL` | `P_Data_Sync_ETL` | 同名 | 标记是否为 DataSync ETL，影响邮件通知内容 |

### 2.3 Kettle Job 内部流程详解

`Standard_ETL.kjb` 内部由 **6 个 entry** 和 **5 条 hop** 组成。

#### 2.3.1 Entry 列表

| # | Entry 名称 | 类型 | 说明 |
|---|---|---|---|
| 1 | `START` | SPECIAL | Job 入口节点 |
| 2 | `Set variables` | SET_VARIABLES | 将 Job 参数（`P_*`）转为 Job 级变量 |
| 3 | `ETL_Specific_To_Addresses` | TRANS | 查询该 ETL 的邮件通知地址 |
| 4 | `Run KTR` | TRANS | 执行实际的数据转换 KTR 文件 |
| 5 | `ETL_Completion_E-Mail - TRUE` | TRANS | KTR 成功时发送完成邮件 |
| 6 | `ETL_Completion_E-Mail - FALSE` | TRANS | KTR 失败时发送失败邮件 |

#### 2.3.2 Hop 链路（执行顺序）

| Hop | From → To | evaluation | unconditional |
|---|---|---|---|
| 1 | START → Set variables | Y | Y（无条件执行） |
| 2 | Set variables → ETL_Specific_To_Addresses | Y | Y（无条件执行） |
| 3 | ETL_Specific_To_Addresses → Run KTR | Y | Y（无条件执行） |
| 4 | Run KTR → ETL_Completion_E-Mail - TRUE | Y（成功分支） | N |
| 5 | Run KTR → ETL_Completion_E-Mail - FALSE | N（失败分支） | N |

#### 2.3.3 "Set variables" 步骤详解

该步骤定义三个变量，作用域均为 `CURRENT_JOB`：

| 变量名 | 值来源 | 说明 |
|---|---|---|
| `Data_Sync_ETL` | `${P_Data_Sync_ETL}` | 直接映射 Job 参数 |
| `ETL_Transformation_Name` | `${P_ETL_Transformation_Name}` | 直接映射 Job 参数 |
| `ETL_Specific_To_Addresses` | `$[20]` | 取上一步（ETL_Specific_To_Addresses.ktr）结果集的第 20 列（0-indexed），即邮件地址 |

> `$[20]` 是 Kettle 的 "get value from previous result row by index" 语法，表示从上游 Transformation 的结果行中取第 21 个字段（索引从 0 开始）。

#### 2.3.4 "Run KTR" 路径拼接

```
${ETL_DIRECTORY}${P_ETL_Transformation_Directory}${P_ETL_Transformation_Name}.ktr
```

- `${ETL_DIRECTORY}` 是 Kettle 内部变量（通常在 `kettle.properties` 中定义，指向 ETL 根目录）
- 拼接示例：`/opt/etl/ETL/` + `Crimes_2001_to_present-ijzp-q8t2/` + `Crimes_2001_to_present-ijzp-q8t2.ktr`

#### 2.3.5 邮件通知

两个邮件 Entry 共用同一个 KTR 文件 `Utilities/ETL_Completion_E-Mail.ktr`，但传入不同的 `P_Body_Start` 参数：

- **TRUE 分支：** "The Kettle transformation for this ETL returned a status of TRUE, meaning that it ran to completion."
- **FALSE 分支：** "The Kettle transformation for this ETL returned a status of FALSE, generally meaning that it did not run to completion. The dataset update or other intended outcome likely was not accomplished."

### 2.4 日志路径

```
../Log/${ETL_NAME}_${NOW}.txt
```

- 相对于 `Standard_ETL.sh` 执行时的工作目录（通常是 `ETL/` 目录），向上一级进入项目根目录，再进入 `Log/` 目录。
- 文件名格式示例：`Crimes_2001_to_present-ijzp-q8t2_20260616_143052.txt`
- 日志级别为 `Detailed`（Kettle 的较高级别，包含详细的步骤执行信息）。
- `${ETL_NAME}` 与 `_` 和 `${NOW}` 之间需要花括号分隔，否则 shell 会将 `$ETL_NAME_` 作为一个整体变量名（`Standard_ETL.sh` 第 9 行的注释明确说明了这一点）。

## 3. 静态验证方法（缺少 Kettle/DataSync 环境时）

当本地没有安装 Kettle（Pentaho Data Integration）或 DataSync 工具时，可以对 Shell 脚本层和 XML 配置进行以下静态验证：

### 3.1 Shell 语法检查

```bash
# 使用 bash -n 进行语法检查（不执行任何命令）
bash -n ETL/ETL_Setup.sh
bash -n ETL/Standard_ETL.sh
bash -n ETL/Setup-Script.sh
```

验证内容：
- 变量赋值语法
- `source`（`.`）命令语法
- 重定向语法（`>`）
- `${}` 花括号变量展开语法

### 3.2 Shell 静态分析（shellcheck）

```bash
# 使用 shellcheck 进行深度静态分析
shellcheck ETL/ETL_Setup.sh
shellcheck ETL/Standard_ETL.sh
shellcheck ETL/Setup-Script.sh
```

可检测的潜在问题：
- **未引用变量：** 如 `$ETL_DIR_RELATIVE` 在 `kitchen.sh` 调用中未加双引号，若路径含空格将导致参数拆分
- **source 路径有效性：** 硬编码的占位路径是否合理
- **位置参数无默认值保护：** `$1`/`$2`/`$3` 在未传参时为空，不会报错但会导致 kitchen.sh 参数缺失

### 3.3 Kettle Job XML 验证

```bash
# 验证 Standard_ETL.kjb 的 XML 格式是否良好
xmllint --noout ETL/Standard_ETL.kjb

# 检查三个必需参数是否在 <parameters> 节点中声明
grep -c "P_ETL_Transformation_Name" ETL/Standard_ETL.kjb        # 预期 >= 1
grep -c "P_ETL_Transformation_Directory" ETL/Standard_ETL.kjb   # 预期 >= 1
grep -c "P_Data_Sync_ETL" ETL/Standard_ETL.kjb                 # 预期 >= 1

# 验证 hop 链路完整性（应有 5 条 hop）
grep -c "<hop>" ETL/Standard_ETL.kjb                            # 预期 = 5

# 验证 entry 数量（应有 6 个 entry）
grep -c "<entry>" ETL/Standard_ETL.kjb                          # 预期 = 6
```

### 3.4 参数一致性交叉验证

确保 Shell 层传出的参数名与 Kettle Job 中声明的参数名完全一致：

```bash
# 提取 kitchen.sh 调用中使用的 -param: 参数名
grep -oP '(?<=-param:)\w+' ETL/Standard_ETL.sh
# 预期输出:
#   P_ETL_Transformation_Directory
#   P_ETL_Transformation_Name
#   P_Data_Sync_ETL

# 提取 Kettle Job 中声明的参数名
grep -oP '(?<=<name>)[^<]+(?=</name>)' ETL/Standard_ETL.kjb | head -3
# 预期输出（顺序可能不同）:
#   P_Data_Sync_ETL
#   P_ETL_Transformation_Directory
#   P_ETL_Transformation_Name

# 两者的集合应完全匹配
```

### 3.5 KTR 文件存在性检查

根据 `Setup-Script.sh` 中配置的 `ETL_NAME` 和 `ETL_DIR_RELATIVE`，验证目标 KTR 文件是否存在：

```bash
# 示例：假设 ETL_NAME=Crimes_2001_to_present-ijzp-q8t2
#       ETL_DIR_RELATIVE=Crimes_2001_to_present-ijzp-q8t2/
test -f "ETL/Crimes_2001_to_present-ijzp-q8t2/Crimes_2001_to_present-ijzp-q8t2.ktr" \
  && echo "KTR exists" || echo "KTR MISSING"
```

### 3.6 工具 KTR 文件存在性检查

```bash
# Standard_ETL.kjb 内部依赖的两个工具 KTR
test -f "ETL/Utilities/ETL_Specific_To_Addresses.ktr" && echo "OK" || echo "MISSING"
test -f "ETL/Utilities/ETL_Completion_E-Mail.ktr"     && echo "OK" || echo "MISSING"
```

### 3.7 日志目录检查

```bash
# 验证日志目录是否存在且可写
test -d "Log/" && echo "Log dir exists" || echo "Log dir MISSING"
test -w "Log/" && echo "Log dir writable" || echo "Log dir NOT writable"
```

### 3.8 占位符完整性检查

所有 `/path/to/` 占位符必须在部署前替换为真实路径：

```bash
# 扫描所有未替换的占位符（排除本分析文档）
grep -rn "/path/to/" ETL/ --include="*.sh"
```

需要替换的位置清单：

| 文件 | 行号 | 占位符 | 应替换为 |
|---|---|---|---|
| `ETL/ETL_Setup.sh` | 第 2 行 | `/path/to/jdk/bin` | 实际 JDK 安装路径下的 `bin` 目录 |
| `ETL/ETL_Setup.sh` | 第 3 行 | `/path/to/directory/open-data-etl-utility-kit/ETL` | ETL 根目录的绝对路径 |
| `ETL/Setup-Script.sh` | 第 1 行 | `/path/to/directory/open-data-etl-utility-kit/ETL/ETL_Setup.sh` | `ETL_Setup.sh` 的绝对路径 |

## 4. 外部环境依赖

### 4.1 必需外部依赖

| 依赖项 | 用途 | 脚本中的引用位置 | 验证方式 |
|---|---|---|---|
| **JDK (Java)** | Kettle 运行在 JVM 上，kitchen.sh 本质是启动 Java 进程 | `ETL_Setup.sh` 第 2 行 `PATH=$PATH:/path/to/jdk/bin` | `java -version` |
| **Pentaho Data Integration (Kettle)** | 执行 `.kjb` Job 和 `.ktr` Transformation | `Standard_ETL.sh` 第 7 行 `../data-integration/kitchen.sh` | 检查 `../data-integration/kitchen.sh` 是否存在且可执行 |
| **kitchen.sh** | Kettle 的命令行 Job 执行器 | 同上 | `test -x ../data-integration/kitchen.sh` |
| **kettle.properties** | 定义 `ETL_DIRECTORY` 等 Kettle 内部变量 | `Standard_ETL.kjb` 中 `${ETL_DIRECTORY}` 引用 | 检查 `~/.kettle/kettle.properties` 或 Kettle 安装目录下的配置文件 |

### 4.3 脚本未显式检查但运行时必需的条件

| 条件 | 说明 |
|---|---|
| `Log/` 目录存在且可写 | 日志重定向 `> "../Log/..."` 在目录不存在时会导致 shell 报错 |
| 目标 KTR 文件存在 | `${ETL_DIRECTORY}${P_ETL_Transformation_Directory}${P_ETL_Transformation_Name}.ktr` 指向的文件必须存在 |
| `Utilities/ETL_Completion_E-Mail.ktr` 存在 | Job 完成后无条件调用此转换发送邮件 |
| `Utilities/ETL_Specific_To_Addresses.ktr` 存在 | Job 启动后在 Set variables 之后立即调用 |
| `kettle.properties` 中定义了 `ETL_DIRECTORY` | KJB 中 Run KTR 步骤的文件路径依赖此变量 |
| 邮件服务器（SMTP）可达 | Kettle 的 Mail 步骤需要 SMTP 连接 |
| DataSync 环境（当 `DATA_SYNC_ETL=Y` 时） | KTR 内部若包含 DataSync 子转换，需要 DataSync 引擎和 datasync.jar |

### 4.4 仅靠静态验证无法确认的部分

以下内容**必须**在有完整运行环境的条件下才能验证：

1. **KTR 转换逻辑正确性** — KTR 文件内部的数据流、步骤配置、数据库连接、API 端点等只能通过 Kettle 引擎执行或在 Spoon GUI 中打开验证。
2. **kitchen.sh 参数传递** — `-param:` 参数是否正确传入 Job、参数值是否被正确解析，只能在运行时确认。
3. **Kettle 内部变量替换** — `${ETL_DIRECTORY}` 等变量的实际值需要在 Kettle 运行时上下文中才能确认（通常定义在 `kettle.properties` 中）。
4. **`$[20]` 取值正确性** — `Set variables` 步骤中 `ETL_Specific_To_Addresses` 变量通过 `$[20]` 从上游结果集取值，需要实际数据才能验证索引是否正确。
5. **邮件通知功能** — 依赖 SMTP 服务器配置、收件人地址查询结果、以及 Kettle 邮件步骤的网络可达性。
6. **DataSync 操作** — 如果 KTR 内部涉及 Socrata DataSync 子转换，需要 DataSync 引擎、datasync.jar、API 凭证和网络连接。
7. **端到端数据正确性** — 源数据可达性、目标 API 可用性、数据转换逻辑的正确性。

## 5. 总结

### 5.1 三层架构

整个 ETL 启动链路是一个三层 Shell 脚本调用结构：

| 层级 | 文件 | 职责 | 修改频率 |
|---|---|---|---|
| 底层 | `ETL_Setup.sh` | 环境基础设施（时间戳、JDK PATH、根目录） | 部署时配置一次，很少修改 |
| 中间层 | `Setup-Script.sh` | 每个 ETL 任务的入口，定义业务参数并串联调用 | 每新建一个 ETL 任务复制一份并修改三个变量 |
| 上层 | `Standard_ETL.sh` | 标准化地调用 Kettle kitchen.sh 并管理日志输出 | 通常不需要修改 |

这种分层设计的好处是：新建一个 ETL 任务只需复制 `Setup-Script.sh` 并修改三个变量（`ETL_NAME`、`ETL_DIR_RELATIVE`、`DATA_SYNC_ETL`），其余的环境配置、Kettle 调用、日志管理和邮件通知全部由公共脚本自动处理。

### 5.2 静态验证 vs 运行时验证

- **静态验证可覆盖的范围：** Shell 语法正确性、变量引用安全性、XML 格式良好性、参数名一致性、文件/目录存在性、占位符残留扫描。
- **必须有完整环境才能验证的范围：** Kettle 参数传递与变量替换、KTR 内部数据流逻辑、邮件发送、DataSync 操作、端到端数据正确性。
