# 标准 ETL 启动链路分析文档

> 本文档基于对 `ETL_Setup.sh`、`Setup-Script.sh`、`Standard_ETL.sh` 以及 `Standard_ETL.kjb` 的静态阅读完成，涵盖完整执行链路、关键参数传递、静态验证方法和外部环境依赖。

---

## 1. 完整执行链路

### 1.1 三层脚本调用关系

```
Setup-Script.sh          （入口层 — 每个具体 ETL 一份）
  ├─ source ETL_Setup.sh （环境层 — 全局公共配置）
  └─ source Standard_ETL.sh $ETL_NAME $ETL_DIR_RELATIVE $DATA_SYNC_ETL
                           （执行层 — 调用 Kettle kitchen.sh）
```

### 1.2 逐层详解

#### 第一层：`ETL_Setup.sh` — 环境初始化

```bash
NOW=$(date +"%Y%m%d_%H%M%S")         # 时间戳，用于日志文件名
PATH=$PATH:/path/to/jdk/bin           # 将 JDK 加入 PATH（Kettle 依赖 Java）
ETL_ROOT_DIR=/path/to/directory/open-data-etl-utility-kit/ETL   # ETL 根目录绝对路径
```

| 变量 | 用途 |
|------|------|
| `NOW` | 日志文件的时间后缀，格式 `YYYYMMDD_HHmmss` |
| `PATH` | 追加 JDK bin 目录，确保 `java` 可被 kitchen.sh 找到 |
| `ETL_ROOT_DIR` | 后续所有路径计算的基准；指向仓库内 ETL 目录 |

> **注意**：`ETL_Setup.sh` 通过 `.`（source）方式加载，所以它设置的变量会留在调用者 shell 环境中。

#### 第二层：`Setup-Script.sh` — 具体 ETL 的入口

```bash
. /path/to/directory/open-data-etl-utility-kit/ETL/ETL_Setup.sh   # source 环境层

ETL_NAME=Name_of_KTR_file_no_extension     # KTR 转换文件名（不含 .ktr）
ETL_DIR_RELATIVE=Directory_containing_KTR_file/   # KTR 所在子目录（相对路径，以 / 结尾）
DATA_SYNC_ETL=Y                            # 是否走 DataSync 流程（Y/N）

echo "ETL $ETL_NAME has started at $NOW."

. $ETL_ROOT_DIR/Standard_ETL.sh $ETL_NAME $ETL_DIR_RELATIVE $DATA_SYNC_ETL
```

| 变量 | 说明 |
|------|------|
| `ETL_NAME` | 目标 Kettle 转换（`.ktr`）的文件名主体 |
| `ETL_DIR_RELATIVE` | 相对于 ETL 根目录的子目录路径，必须以 `/` 结尾 |
| `DATA_SYNC_ETL` | 标志位；`Y` 表示该 ETL 涉及 DataSync（影响邮件通知内容） |

#### 第三层：`Standard_ETL.sh` — 调用 kitchen.sh

```bash
ETL_NAME=$1
ETL_DIR_RELATIVE=$2
DATA_SYNC_ETL=$3

../data-integration/kitchen.sh \
  -file="$ETL_ROOT_DIR/Standard_ETL.kjb" \
  -param:P_ETL_Transformation_Directory=$ETL_DIR_RELATIVE \
  -param:P_ETL_Transformation_Name=$ETL_NAME \
  -param:P_Data_Sync_ETL=$DATA_SYNC_ETL \
  -level=Detailed \
  > "../Log/${ETL_NAME}_${NOW}.txt"
```

**参数传递链**：

| Shell 变量 | Kettle Job 参数 | 在 KJB 中的使用 |
|------------|-----------------|----------------|
| `$ETL_DIR_RELATIVE` | `P_ETL_Transformation_Directory` | 拼接到 `${ETL_DIRECTORY}${P_ETL_Transformation_Directory}${P_ETL_Transformation_Name}.ktr` |
| `$ETL_NAME` | `P_ETL_Transformation_Name` | 同上，定位目标 `.ktr` 文件 |
| `$DATA_SYNC_ETL` | `P_Data_Sync_ETL` | 传递给邮件通知，标识是否为 DataSync ETL |

**日志路径**：`../Log/${ETL_NAME}_${NOW}.txt`（相对于 `ETL_ROOT_DIR` 的上级目录的 `Log/` 文件夹）。`${ETL_NAME}` 与 `${NOW}` 之间的花括号 `{}` 确保 shell 能正确区分两个变量名（否则 `$ETL_NAME_$NOW` 会被解析为 `$ETL_NAME_` + `$NOW`）。

### 1.3 Standard_ETL.kjb 内部执行流程

`Standard_ETL.kjb` 是一个 Kettle Job XML 文件，其内部节点按 `<hops>` 定义的顺序执行：

```
START
  │ (unconditional)
  ▼
Set variables                 ← 将 Job 参数映射为 Kettle 变量
  │                           - Data_Sync_ETL = ${P_Data_Sync_ETL}
  │                           - ETL_Transformation_Name = ${P_ETL_Transformation_Name}
  │                           - ETL_Specific_To_Addresses = $[20]
  │ (unconditional)
  ▼
ETL_Specific_To_Addresses     ← 运行辅助转换，获取邮件收件人地址
  │ (unconditional)
  ▼
Run KTR                       ← 核心步骤：执行目标 .ktr 转换
  │                             路径: ${ETL_DIRECTORY}${P_ETL_Transformation_Directory}
  │                                     ${P_ETL_Transformation_Name}.ktr
  │
  ├─ evaluation=Y (成功) ──► ETL_Completion_E-Mail - TRUE
  │                          发送"执行成功"通知邮件
  │
  └─ evaluation=N (失败) ──► ETL_Completion_E-Mail - FALSE
                             发送"执行失败"通知邮件
```

**关键细节**：
- `${ETL_DIRECTORY}` 变量（注意不是 `ETL_ROOT_DIR`）在 Kettle 内部设置，指向 ETL 根目录。
- `$[20]` 是 Kettle 内部变量引用语法，指向 `ETL_Specific_To_Addresses` 转换的输出。
- `pass_all_parameters=Y` 表示所有 Job 参数会向下传递到子转换。

### 1.4 端到端完整链路总结

```
┌──────────────────────────────────────────────────────────────┐
│  Setup-Script.sh (具体 ETL 入口)                              │
│                                                              │
│  1. source ETL_Setup.sh                                      │
│     → NOW, PATH(+JDK), ETL_ROOT_DIR                         │
│                                                              │
│  2. 定义 ETL_NAME, ETL_DIR_RELATIVE, DATA_SYNC_ETL          │
│                                                              │
│  3. source Standard_ETL.sh (三个参数)                         │
│     → ../data-integration/kitchen.sh                         │
│       -file=Standard_ETL.kjb                                 │
│       -param:P_ETL_Transformation_Directory                  │
│       -param:P_ETL_Transformation_Name                       │
│       -param:P_Data_Sync_ETL                                 │
│       -level=Detailed                                        │
│       > ../Log/${ETL_NAME}_${NOW}.txt                        │
│                                                              │
│  4. KJB 内部:                                                │
│     Set variables → ETL_Specific_To_Addresses                │
│     → Run KTR → E-Mail (TRUE/FALSE)                         │
└──────────────────────────────────────────────────────────────┘
```

## 2. 静态验证方法（本地缺少 Kettle / DataSync 时）

### 2.1 Shell 语法验证

对所有 `.sh` 文件进行纯语法检查，不需要任何外部依赖：

```bash
# 使用 bash -n 做语法检查（不执行）
bash -n ETL/ETL_Setup.sh
bash -n ETL/Setup-Script.sh
bash -n ETL/Standard_ETL.sh
```

若输出为空则表示语法正确；有语法错误时会报出行号和错误类型。

### 2.2 Shell 静态分析（ShellCheck）

使用 [ShellCheck](https://www.shellcheck.net/) 进行更深入的分析：

```bash
shellcheck ETL/ETL_Setup.sh ETL/Setup-Script.sh ETL/Standard_ETL.sh
```

可发现的问题类型：
- 变量未加引号（如 `$ETL_NAME` 应为 `"$ETL_NAME"`）
- source 路径硬编码问题
- 未使用/未定义的变量警告

### 2.3 变量与参数一致性校验

手动核查以下映射关系是否匹配：

| 检查项 | 方法 |
|--------|------|
| Setup-Script.sh 中 `ETL_NAME` 对应的 `.ktr` 文件是否存在 | `ls ETL/${ETL_DIR_RELATIVE}${ETL_NAME}.ktr` |
| `ETL_DIR_RELATIVE` 是否以 `/` 结尾 | 正则检查 `[[ "$ETL_DIR_RELATIVE" == */ ]]` |
| `DATA_SYNC_ETL` 是否为 `Y` 或 `N` | 值域校验 |
| Standard_ETL.kjb 中三个 `<parameter>` 名是否与 kitchen.sh 的 `-param:` 一致 | XML 静态解析（见下方） |

### 2.4 KJB XML 静态校验

`Standard_ETL.kjb` 是标准 XML，可以用 `xmllint` 做结构验证：

```bash
# 检查 XML 格式是否合法
xmllint --noout ETL/Standard_ETL.kjb

# 验证参数定义是否完整
xmllint --xpath '//parameters/parameter/name/text()' ETL/Standard_ETL.kjb
```

预期输出三个参数名：`P_Data_Sync_ETL`、`P_ETL_Transformation_Directory`、`P_ETL_Transformation_Name`。

### 2.5 文件引用完整性检查

验证 KJB 中引用的所有 `.ktr` 文件是否在仓库中存在：

```bash
# 从 KJB 中提取所有 filename 引用并检查文件是否存在
grep -oP '(?<=<filename>)[^<]+' ETL/Standard_ETL.kjb | \
  sed 's/\${ETL_DIRECTORY}/ETL/g; s/&#47;/\//g' | \
  while read f; do
    [ -f "$f" ] && echo "OK: $f" || echo "MISSING: $f"
  done
```

### 2.6 Dry-Run 模拟（不实际执行 Kettle）

创建一个 kitchen.sh 的 mock 脚本来捕获调用参数：

```bash
#!/bin/bash
# mock_kitchen.sh — 放到 ../data-integration/ 下
echo "[MOCK] kitchen.sh called with arguments:"
for arg in "$@"; do
  echo "  $arg"
done
echo "[MOCK] Would run: file=$1, params=$2 $3 $4, level=$5"
exit 0
```

将其命名为 `kitchen.sh` 放在 `data-integration/` 目录，然后正常执行 `Setup-Script.sh`，可以验证：
- 变量展开是否正确
- 参数拼接是否符合预期
- 日志路径是否可写

## 3. 外部环境依赖

以下部分**必须**在完整环境中才能真正运行：

| 依赖项 | 用途 | 影响范围 |
|--------|------|---------|
| **JDK / JRE** | Kettle（Pentaho Data Integration）运行在 Java 上 | `PATH` 中需要 `java` 命令 |
| **Pentaho Data Integration (data-integration/)** | 提供 `kitchen.sh`（Job 执行器）和 `pan.sh`（转换执行器） | `Standard_ETL.sh` 第 7 行直接调用 `../data-integration/kitchen.sh` |
| **ETL_DIRECTORY 变量** | Kettle 内部变量，指向 ETL 根目录 | KJB 中所有 `.ktr` 路径的前缀 |
| **目标数据源** | 各 `.ktr` 转换中配置的数据库连接、API 端点、FTP/HTTP 服务器 | 实际 ETL 数据抽取 |
| **SMTP 邮件服务** | `ETL_Completion_E-Mail.ktr` 发送完成通知 | Job 最后一步 |
| **Log 目录** | `../Log/` 目录需要存在且可写 | 日志输出重定向 |

### 3.1 依赖关系图

```
                    ┌─────────────┐
                    │   JDK/JRE   │  ← 必须在 PATH 中
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  kitchen.sh │  ← Pentaho data-integration 目录
                    └──────┬──────┘
                           │
              ┌────────────▼────────────┐
              │    Standard_ETL.kjb     │
              ├─────────────────────────┤
              │ 内部步骤:               │
              │  1. Set variables       │
              │  2. ETL_Specific_To_    │
              │     Addresses.ktr       │  ← 需要存在
              │  3. Run KTR (目标转换)   │  ← 需要存在 + 数据源可达
              │  4. ETL_Completion_     │
              │     E-Mail.ktr          │  ← 需要 SMTP 服务
              └────────────┬────────────┘
                           │
                    ┌──────▼──────┐
                    │  ../Log/    │  ← 目录需存在且可写
                    └─────────────┘
```

### 3.2 本地开发 vs 服务器运行的差异

| 方面 | 本地（无 Kettle） | 服务器（完整环境） |
|------|-------------------|-------------------|
| Shell 语法验证 | `bash -n` / ShellCheck | 同左 |
| XML 结构验证 | `xmllint` | 同左 |
| 文件引用检查 | grep + 文件系统检查 | 同左 |
| 参数传递验证 | mock kitchen.sh | 真实 kitchen.sh |
| KTR 转换逻辑验证 | **不可行** — 需 Spoon GUI 或 Kettle 引擎 | kitchen.sh / pan.sh 执行 |
| DataSync 流程 | **不可行** — 需外部数据源和同步目标 | 完整执行 |
| 邮件通知 | **不可行** — 需 SMTP | 自动发送 |

## 4. 关键配置说明

### 4.1 新增一个具体 ETL 的步骤

1. 在 `ETL/` 下创建目标 `.ktr` 转换文件（可用 `ETL_Template.ktr` 作为模板）。
2. 复制 `Setup-Script.sh` 为新的入口脚本，修改三个变量：
   - `ETL_NAME` = 你的 `.ktr` 文件名（不含扩展名）
   - `ETL_DIR_RELATIVE` = `.ktr` 所在子目录（相对 ETL 根目录，以 `/` 结尾）
   - `DATA_SYNC_ETL` = `Y` 或 `N`
3. 确保 `ETL_Setup.sh` 中的路径已正确配置。
4. 运行入口脚本。

### 4.2 _control.json 的作用

`_control.json` 定义了 Socrata DataSync 的 CSV 解析配置，包含：
- 列名映射（`columns` 数组 — 需替换为实际 API 字段名）
- CSV 分隔符、编码、引号字符
- 时间戳格式
- 操作类型（`action: "Replace"` 表示全量替换目标数据集）

此文件在 DataSync 类 ETL（`DATA_SYNC_ETL=Y`）中被 Socrata 平台消费。

```

├── ETL/
│   ├── ETL_Setup.sh              ← 环境层：全局变量
│   ├── Setup-Script.sh           ← 入口层：具体 ETL 模板

│   ├── Standard_ETL.kjb          ← Kettle Job 定义（XML）
│   ├── ETL_Template.ktr          ← KTR 转换模板
│   ├── _control.json             ← DataSync CSV 配置
│   └── Utilities/

│       ├── DataSyncFTP.ktr
│       ├── DataSyncHTTP.ktr
```
